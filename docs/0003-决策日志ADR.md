## ADR-001: 项目命名 TradeNest

**状态**: Accepted
**日期**: 2026-05-13

### 背景

需要给项目定一个名字，要陪伴 1-3-5 年使用。要求：
- 见名知义（投资圈一秒懂）
- 不撞名（GitHub / 域名）
- 调性匹配产品哲学（长期陪伴、记忆归宿）
- 不踩合规红线（不暴露"投顾"等敏感词）

### 决策

**TradeNest** = Trade（投资 / 交易）+ Nest（巢穴 / 归宿）

### 理由

1. **见名知义**：投资圈听到 Trade 一秒懂
2. **完美贴合定位**：Nest = 你所有研究的"家"，对应 5 层记忆
3. **GitHub 完全干净**：搜 `tradenest` 无超过 5 stars 的项目
4. **不踩合规线**：避开 "Invest"、"Stock"、"Adviser" 等敏感词
5. **可扩展性**：未来不限于股票，可扩展到基金/数字资产/任何研究领域

### 候选方案

| 名字 | 评分 | 否决原因 |
|------|------|---------|
| Investia | 6/10 | 偏 2018 年风格，俗 |
| Almanac | 9.5/10 | 太文艺，不见名知义 |
| AlphaBook | 8/10 | 拼接牵强 |
| TradeMemo | 8/10 | 撞 mnemox-ai/tradememory（874 stars） |
| TradeNote | 7/10 | 撞 Eleven-Trading/TradeNote（828 stars） |
| TradeJournal | 7/10 | 朴素但平 |
| TradeVault | 8/10 | 偏静态保险库感 |
| TradeSage | 7/10 | "贤者"暗示给建议，跟产品哲学冲突 |
| TradeDeck | 7/10 | 操作台感，偏交易非研究 |
| **TradeNest** | **9/10** | **采用** |

### 后果

**优势**：
- 域名候选 tradenest.app / .ai / .dev 大概率可注册
- 故事讲得通："Where your investment ideas come home to grow"
- 简历 / 对外讲故事时清晰

**风险**：
- "Trade" 一词可能被部分人误以为"交易/操盘工具"——通过营销澄清

### 备注

GitHub 仓库名 `tradenest` 全小写。
Python 包名 `tradenest`。
产品对外名 `TradeNest`（驼峰）。

## ADR-002: 用 Anthropic SDK + LangGraph 混合

**状态**: Accepted
**日期**: 2026-05-13

### 背景

需要选 Agent 编排框架。2026 年的主流框架：
- LangGraph（LangChain 出品）
- Anthropic Claude Agent SDK（2026.3 发布）
- OpenAI Agents SDK（2026.3 发布）
- Google ADK（2026.4 发布）
- CrewAI
- AutoGen

### 决策

**主用 Anthropic Claude Agent SDK，复杂状态机用 LangGraph**

```python
# 简单 Agent loop → Anthropic SDK
from anthropic import AsyncAnthropic

# 复杂多 Agent 编排（多空辩论 / 风控辩论） → LangGraph
from langgraph.graph import StateGraph, END
```

### 理由

1. **Anthropic SDK 跟 Claude Code 同源**——满足"用上 cc 最新技术"目标
2. **LangGraph 状态机能力最强**——多 Agent 辩论需要复杂控制流
3. **两者可共存**——SDK 做 Agent loop，LangGraph 做 orchestration
4. **生产级稳定**——LangGraph 是 2026 年生产 Agent 框架的事实标准

### 候选方案

| 框架 | 优势 | 劣势 | 评估 |
|------|------|------|------|
| Anthropic SDK 单用 | 简单、贴近 cc | 复杂编排弱 | 不够 |
| LangGraph 单用 | 编排强 | 离 Claude Code 生态远 | 缺乏 cc 风味 |
| OpenAI Agents SDK | 官方背书 | 偏 OpenAI 生态 | 不优先 |
| CrewAI | 角色导向、上手快 | 控制粒度粗 | 不够 |
| AutoGen | 多 Agent 辩论强 | 学习曲线高、风格冗长 | 不优先 |
| 自己写 | 最纯粹 | 工作量爆炸 | 不必 |
| **SDK + LangGraph 混合** | **结合两者优势** | **学两套 API** | **采用** |

### 后果

**优势**：
- Day 1 MVP 简单（Anthropic SDK 跑通）
- 后期复杂编排有保证（LangGraph）
- 跟 Claude Code 思路一致

**风险**：
- 两套 API 学习曲线
- 两个依赖的版本兼容性

**缓解**：
- pyproject.toml 锁定版本
- 渐进式引入 LangGraph（Phase 2 才用）

### 备注

Day 1 mvp.py 只用 Anthropic SDK；Phase 2 引入 LangGraph 做多 Agent 辩论。

## ADR-003: 桌面用 Tauri 2.x，不用 Electron

**状态**: Accepted
**日期**: 2026-05-13

### 背景

需要选桌面客户端框架。主流方案：
- Tauri 2.x（Rust 主进程 + 系统 webview）
- Electron（Chromium + Node.js）
- Flutter Desktop
- 原生（Swift / C# / Qt）

### 决策

**Tauri 2.x**

### 理由

1. **包体积**：Tauri ~10MB vs Electron ~100MB
2. **内存占用**：Tauri 显著更低
3. **性能**：Rust 主进程更快
4. **现代趋势**：2025-2026 年新项目首选 Tauri
5. **跨平台**：Mac / Win / Linux 全支持
6. **安全性**：默认更严格的权限模型

### 候选方案

| 方案 | 包大小 | 性能 | 生态 | 评估 |
|------|-------|------|------|------|
| Tauri 2.x | ~10MB | 高 | 良好（增长中） | ✅ 采用 |
| Electron | ~100MB | 中 | 极好 | 太重 |
| Flutter Desktop | ~50MB | 高 | 中（移动为主）| 不优先 |
| 原生 | 极小 | 极高 | 各平台不同 | 工作量爆炸 |

### 后果

**优势**：
- 用户安装包小，分发友好
- 长期使用内存占用低

**风险**：
- Tauri 生态不如 Electron 成熟
- Rust 的学习曲线（虽然主要写 TS）

**缓解**：
- 大部分代码在前端 React，Rust 部分最少化
- 关键功能（文件、数据库连接）用 Tauri 官方插件

## ADR-004: 后端用 Python，不用 TypeScript

**状态**: Accepted
**日期**: 2026-05-13

### 背景

后端语言选择：
- Python（主流 AI / 金融数据生态）
- TypeScript（Node.js）
- Go（高性能）
- Rust（极致性能）

### 决策

**Python 3.12**

### 理由

1. **金融数据生态完整**：AkShare / Tushare / Pandas / NumPy 都是 Python
2. **数值计算精度**：Decimal 模块成熟
3. **多 Agent 框架**：LangGraph / AutoGen / CrewAI 都是 Python first
4. **LLM SDK 优先级**：Anthropic / OpenAI 等 Python SDK 通常更新更早
5. **作者已有经验**：Python 生态熟悉

### 候选方案

| 语言 | 金融生态 | LLM 生态 | 性能 | 评估 |
|------|---------|---------|------|------|
| Python 3.12 | ✅ 完整 | ✅ 一线 | 中 | ✅ 采用 |
| TypeScript | ❌ 几乎没 | ✅ 一线 | 中 | 否 |
| Go | ❌ 弱 | ⚠️ 中等 | 高 | 否 |
| Rust | ❌ 几乎没 | ⚠️ 中等 | 极高 | 否 |

### 后果

**优势**：
- AkShare / Tushare 直接用
- LangGraph 等框架原生支持
- 开发速度快

**风险**：
- Python 性能在高并发场景一般
- GIL 限制

**缓解**：
- 用 asyncio 处理 I/O
- 性能瓶颈处用 Rust 写扩展（PyO3）

## ADR-005: 用 PG + pgvector，不用 Milvus / Weaviate

**状态**: Accepted
**日期**: 2026-05-13

### 背景

需要存储：
- 关系数据（用户 / 笔记 / 决策 / 对话）
- 向量数据（笔记 / 对话的语义检索）

### 决策

**PostgreSQL 16 + pgvector 扩展**

### 理由

1. **一栈搞定**：PG 同时存关系 + 向量，不需多套系统
2. **运维简单**：单一数据库，备份恢复简单
3. **2026 年 pgvector 已成熟**：HNSW / IVFFlat 都支持
4. **TimescaleDB 扩展**：未来时序数据可以无缝扩展
5. **本地优先适配**：PG 本地跑无门槛

### 候选方案

| 方案 | 关系 | 向量 | 运维 | 评估 |
|------|------|------|------|------|
| PG + pgvector | ✅ | ✅ | 简单 | ✅ 采用 |
| PG + Milvus | ✅ | ✅ | 复杂（两个系统） | 否 |
| MongoDB（仿 TradingAgents-CN） | ⚠️ | ⚠️（需插件） | 中 | 否 |
| Weaviate | ❌ | ✅ | 中 | 否 |

### 后果

**优势**：
- 数据库一致性好
- 减少运维复杂度
- 向量索引性能足够（中等数据量）

**风险**：
- 单点 PG 在超大向量数据集时不如专用向量库

**缓解**：
- v1 数据规模小（个人使用），PG 完全足够
- 真到瓶颈再迁移（YAGNI 原则）

## ADR-006: 用 uv 管理 Python 依赖

**状态**: Accepted
**日期**: 2026-05-13

### 背景

Python 包管理选择：
- pip + venv
- poetry
- pdm
- **uv**（Astral 出品，2024 大火）

### 决策

**uv**

### 理由

1. **速度极快**：比 pip + poetry 快 10-100 倍
2. **统一工具**：一个 `uv` 命令搞定 venv / install / lock / publish
3. **2026 主流**：新项目大量采用
4. **Workspace 支持**：天然支持 monorepo

### 候选方案

| 工具 | 速度 | 生态 | 评估 |
|------|------|------|------|
| pip | 慢 | 老牌 | 否 |
| poetry | 中 | 主流 | 不够快 |
| pdm | 快 | 中 | 候选 |
| **uv** | **极快** | **新主流** | **采用** |

### 后果

**优势**：依赖安装从分钟级到秒级，开发体验显著提升。

**风险**：相对较新，部分长尾问题可能没解决。

## ADR-007: 不集成 TradingAgents-CN 代码

**状态**: Accepted
**日期**: 2026-05-13

### 背景

TradingAgents-CN（github.com/hsliuping/TradingAgents-CN, 26554 stars）是中文 AI 投资分析的明星项目，核心 `tradingagents/` 包是 Apache 2.0。可以直接 import 使用。

### 决策

**不直接 import，但深度借鉴业务设计**

### 理由

1. **学习目的**：项目目标是"用上 cc 全部核心技术"——抄代码达不到这个目的
2. **架构差异**：TradingAgents-CN 是 Web 单次分析，我们是桌面长期陪伴
3. **技术栈差异**：他们 FastAPI + Vue + MongoDB；我们 FastAPI + Tauri + PG
4. **可控性**：自己写代码可以深度改进 / 集成 5 层记忆
5. **品牌独立**：避免被认为是 fork

### 候选方案

| 方案 | 优势 | 劣势 | 评估 |
|------|------|------|------|
| 直接 fork | 起步快 | 难独立演进 / 学不到东西 | 否 |
| 当作依赖 import | 节省工程 | 受其架构约束 / 集成难度 | 否 |
| 不用代码，借鉴设计 | 自主、学到、可定制 | 工作量大 | ✅ 采用 |
| 完全独立设计 | 极致自主 | 重复造轮子 | 不必 |

### 后果

**优势**：
- 技术沉淀真实
- 完全可控
- 跟我们的 5 层记忆架构深度集成

**风险**：
- 工作量比 fork 大 2-3 倍
- 可能"造劣质轮子"

**缓解**：
- 业务流程严格借鉴 TradingAgents-CN（5 分析师 / 多空 / 风控）
- 重点投入"我们独有的"差异化（5 层记忆 / 苏格拉底 / 推送）

### 备注

详细的"借鉴 vs 不借鉴"清单见 [REFERENCES.md](./0004-参考项目分析.md)。

## ADR-008: 5 层持久记忆系统设计

**状态**: Accepted
**日期**: 2026-05-13

### 背景

需要为长期陪伴产品设计记忆系统。主流方案：
- 单层 Memory（OpenAI Memory）
- 简单 RAG（笔记向量化）
- 长上下文（1M tokens）

### 决策

**5 层分层记忆**：
- L1 用户画像（你是谁）
- L2 研究框架（你的"公式"）
- L3 研究笔记（你研究了什么）
- L4 决策档案（你做了什么决定）
- L5 对话历史（你跟 AI 怎么聊的）

### 理由

1. **分层显式**：避免单层 RAG 的"什么都是 chunk"问题
2. **语义清晰**：每层有明确语义和用途
3. **可控可解释**：用户能看到 AI 在用哪层记忆
4. **借鉴 cc 思路**：Claude Code 的 Memory Tool / Auto Memory 思路

### 候选方案

| 方案 | 结构 | 评估 |
|------|------|------|
| 单层 Memory | 平 | 太简单，丢结构 |
| 2 层（事实 + 偏好） | 简单 | 不够细 |
| 5 层（我们的） | 分层语义 | ✅ 采用 |
| 7+ 层 | 太细 | YAGNI |

### 后果

**优势**：
- 分析时可以精准加载所需记忆
- 用户可以独立编辑各层
- 跨会话连续性好

**风险**：
- 实现复杂度高于单层

**缓解**：
- 分阶段实现（Phase 1 实现 L1+L3+L5，Phase 2 加 L2+L4）

## ADR-009: 桌面客户端 + 浏览器扩展双形态

**状态**: Accepted
**日期**: 2026-05-13

### 背景

产品形态选择：
- 仅 Web
- 仅桌面
- 桌面 + 扩展
- 桌面 + 移动 + Web

### 决策

**桌面客户端为主 + 浏览器扩展为辅**（v1）

### 理由

1. **桌面是主战场**：投资研究在 PC 上做（看研报 / 看年报 / 写笔记）
2. **扩展是入口**：在雪球 / 东财 / 微信看研究时一键存到 TradeNest
3. **避免分散精力**：移动端 v2 再说

### 候选方案

| 方案 | 优势 | 劣势 | 评估 |
|------|------|------|------|
| 仅 Web | 部署简单 | 离线不可用 | 否 |
| 仅桌面 | 完整 | 缺少入口 | 不够 |
| 桌面 + 扩展 | 完整 + 入口 | 工作量中 | ✅ 采用 |
| 桌面 + 扩展 + 移动 | 全平台 | 工作量爆炸 | v2 再说 |

## ADR-011: 主模型 Claude Sonnet 4.6

**状态**: Accepted
**日期**: 2026-05-13

### 背景

LLM 主模型选择。2026 年 5 月可选：
- Claude Sonnet 4.6 / Opus 4.7
- GPT-5
- Gemini 3.1 Pro
- DeepSeek V3.2
- Qwen3 Coder Plus

### 决策

**默认 Claude Sonnet 4.6，重要场景用 Opus 4.7，备选 DeepSeek / Qwen / GPT-5**

### 理由

1. **跟 cc 同源**：满足"用上 Claude Code 技术"目标
2. **agentic 性能强**：Anthropic 在 Agent 训练上投入最多
3. **1M context**：5 层记忆需要长上下文
4. **价格合理**：Sonnet 4.6 性价比好

### 候选方案

| 模型 | 用途 | 价格 | 评估 |
|------|------|------|------|
| **Claude Sonnet 4.6** | 默认 | 中等 | ✅ 主用 |
| **Claude Opus 4.7** | 复杂分析 | 高 | ✅ 关键场景 |
| GPT-5 | 备选 | 中 | ✅ 备选 |
| Gemini 3.1 Pro | 备选 | 中 | ⚠️ 备选 |
| **DeepSeek V3.2** | 经济模式 | 低 | ✅ 经济模式 |
| **Qwen3** | 国内场景 | 低 | ✅ 国内备选 |

### 后果

- 多 Provider 路由（按任务复杂度选模型）
- 用户可以配置自己偏好的模型
- 失败降级链：Anthropic → OpenAI → DeepSeek

## ADR-012: 数据源 AkShare 起步

**状态**: Accepted
**日期**: 2026-05-13

### 背景

A 股数据源：
- AkShare（开源）
- Tushare Pro（部分免费 + 收费）
- 自建爬虫（东方财富 / 雪球）
- 万得 / 同花顺 API（贵）

### 决策

**主用 AkShare，Tushare 作为可选升级**

### 理由

1. **完全免费**：个人项目预算友好
2. **覆盖广**：A 股 / 港股 / 美股 / 期货 / 基金都有
3. **社区活跃**：维护良好
4. **零门槛**：无需 Token

### 后果

**优势**：开发友好。

**风险**：AkShare 抓的是公开页面，部分接口稳定性一般。

**缓解**：
- 多接口降级链
- Tushare Pro 作为备选（用户可配 Token）

## ADR-013: Playwright 走用户本地浏览器

**状态**: Accepted
**日期**: 2026-05-13

### 背景

抓取需要登录的内容（雪球 / 微信公众号 / 知乎）：
- 用户提供账号密码（合规风险）
- 用 Cookie 文件
- **走用户本地 Chrome / Edge profile**

### 决策

**Playwright `launch_persistent_context` 用用户本地浏览器 profile**

### 理由

1. **合规**：用户自己的登录态，TradeNest 不存密码
2. **稳定**：不大规模爬虫，避免封号
3. **真实**：拿到的就是用户能看到的内容

### 后果

- 仅在用户机器上跑（不能云端）
- 桌面客户端定位被强化

## ADR-014: 苏格拉底对话不替决策

**状态**: Accepted
**日期**: 2026-05-13

### 背景

AI 对话风格选择：
- 给具体建议（"建议买入"——违法）
- 暗示性建议（"看好"——灰区）
- 中立分析（"两边说"——无用）
- **苏格拉底反问**（强迫用户想清楚）

### 决策

**苏格拉底式反问**——不给答案，问问题

### 理由

1. **合规**：完全规避投顾红线
2. **产品哲学**：让用户成长比代用户决策更有价值
3. **差异化**：跟所有同类产品区分
4. **对作者本人有用**：dogfood 验证

### 后果

**优势**：
- 合规清晰
- 产品定位有特色
- 真正帮助用户

**风险**：
- 部分"伸手党"用户会觉得"AI 不告诉我"难用——但他们不是目标用户

## ADR-017: dogfood 优先

**状态**: Accepted
**日期**: 2026-05-13

### 背景

个人项目最大风险：作者放弃。原因通常是"作者不真用产品"。

### 决策

**作者本人是首要用户**。每个功能问"我自己用不用"，不用就砍。

### 理由

1. 验证需求真实
2. 持续动力来源
3. 反馈回路最短

### 后果

- 任何功能首先服务作者本人 Persona
- v1 不为"假设用户"做功能

## ADR-018: 文档驱动开发

**状态**: Accepted
**日期**: 2026-05-13

### 背景

8 个月的项目，需要保证：
- 接手者（人 / AI）能快速进入
- 重要决策不丢失
- 合规有据可查

### 决策

**13 份核心文档** + ADR 流程：
- README / PRD / DECISIONS / REFERENCES / COMPLIANCE
- ARCHITECTURE / TECH-STACK / DATA-MODEL / AGENT-DESIGN
- ROADMAP / AGENTS / CONTRIBUTING / CHANGELOG
- 重大决策必须写新 ADR

### 后果

**优势**：项目可持续 + 接手友好。

**风险**：文档维护成本——通过"代码改动同时改文档"的纪律解决。
